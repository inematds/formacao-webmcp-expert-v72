Lesson 6 · 15 min

Living with an API that changes: watch the spec, Chrome Status and the MCP changelog

The WebMCP API has already moved once: from navigator to document. It will change again before any stable release. Instead of finding out from a visitor, record what the sources said on the day the test suite passed and let a script compare. Changed? Run the test suite and read it before touching anything.

Start the lesson

In this lesson you will

  2. 2What to watch: spec, Chrome Status, MCP and the SDK
  3. 3The recorded baseline and the comparison
  4. 4What to do when the watch says MUDOU

Goal: record the baseline from the day the test suite passed and watch the spec, Chrome Status and MCP, with the navigator → document case as an example.

02 · What to watch and where

Public pages, no key and no cost.

1. Spec

The date at the top of the draft and the IDL names (registerTool, getTools, executeTool, toolchange).

Old name coming back or a new method showing up: time to reread.

Sourcewebmachinelearning.github.io/webmcp

2. Chrome Status

The status ("Proposed" on 10/19/2026) and the origin trial versions (149 to 156).

The trial ends at 156: note it in your calendar, along with the token.

SourcePublic Chrome Status JSON, entry 5117755740913664

3. MCP

The versioning page gives the current revision (2026-07-28) and the changelog says what changed.

The Registry is in preview, with a notice of changes and resets: don't depend on it.

4. Your SDK

The kit's server answers server/discover with the revisions it speaks (2026-07-28).

Package version always pinned; upgrading is a decision, with the battery first.

06 · Practice

Watch, see a real change, and save your own baseline.

3 min

Done when: node scripts/vigiar.mjs; echo "saída: $?" → VIGIA: 7/7 iguais à base · nada a fazer and saída: 0 as long as nothing has changed since 10/19/2026; with a change, MUDOU lines and saída: 1.
