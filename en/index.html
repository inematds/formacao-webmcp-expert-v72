WebMCP in production: page, server, test battery, and report

Serve the same action through the screen, through WebMCP on the page, and through an MCP server, with a single rule. Log every call, freeze the test battery, watch the spec, and turn off a tool without a deploy. WebMCP is a draft as of 10/16/2026: production here means preparing with tests, not betting.

The lessons

From the 8 layers to the report: three surfaces, log, frozen test battery, neighboring protocols, spec watcher, and governance.

  1. Lesson 1 · 14 minLayered architecture revisited with the state as of Oct 2026A site ready for agents is not an API: it is eight layers, from the ones that describe the site to the ones that protect it. The WebMCP track already had this map; here it comes back with the status of each layer as of 10/19/2026 and a script that searches your code for the evidence of each one.
  2. Lesson 2 · 18 minOne action, three surfaces: HTML, WebMCP on the page, and MCP on the serverThe same booking can arrive through the person on the form, through an agent inside the browser (WebMCP), or through an agent outside it (MCP). If each path has its own copy of the rule, they drift apart. In this lesson the rule lives in a single file, and a script proves that the three surfaces respond the same way and ask for the person.
  3. Lesson 3 · 15 minObservability: logging calls, errors, and cancellationsIn production, "the agent couldn't book" only gets solved with a log. Every tool call, through any door, leaves a line: surface, tool, result, and time. No personal data. In this lesson you trigger the possible outcomes and read what each one leaves in the log.
  4. Lesson 4 · 18 minA frozen battery for your tools, and regression when the spec changesWhen the code or the spec changes, a site with WebMCP fails silently: detection does not find the API, falls back to the form, and nobody notices. Only a battery catches it. In this lesson you freeze the contract and the cases for the tools, run them in all four modes, and watch the battery catch the old API name.
  5. Lesson 5 · 14 minNeighbor protocols as a map: A2A, ACP, AP2, NLWeb, llms.txt — what is still a draftEvery week a new acronym shows up promising to make your site "AI-ready." Almost all of them are drafts or proposals, and each one lives in a different layer. In this lesson you place each neighbor protocol on the map, with a status and a date, and decide for your site: adopt, wait, or does not apply.
  6. Lesson 6 · 15 minLiving with an API that changes: watch the spec, Chrome Status and the MCP changelogThe WebMCP API has already moved once: from navigator to document. It will change again before any stable release. Instead of finding out from a visitor, record what the sources said on the day the test suite passed and let a script compare. Changed? Run the test suite and read it before touching anything.
  7. Lesson 7 · 16 minProduction and governance: who approves a new tool, versioning, shutting it off fastA tool for an agent is an action on your site performed by someone else. It needs an owner, an approval date, an autonomy level, and a way to go offline in minutes without breaking the form. In this lesson the approved catalog becomes a file that the page and the server read, a script checks it, and a state shuts a tool off.
  8. Lesson 8 · 20 minFinal project: your site + server + battery + reportThe final project brings the pieces together: the page with tools, the MCP server with the same rule, the frozen battery, the log, the watch, and the approved catalog. One script runs the seven checks and writes your site's dated report. You leave with it and with the maintenance plan for when the spec changes.

Who it's for

  1. 1People who took course 2 (WebMCP on the page) and course 4 (security), or who already register tools and run an MCP server.
  2. 2A dev or technical owner who will maintain a site used by agents for months, with the API still changing.
  3. 3People who want to prove with a test, not a screenshot, that the site works with and without an agent.

What you'll be able to do

  1. 1Serve one action through the screen, through WebMCP, and through MCP with the same rule.
  2. 2Log calls, errors, refusals, and cancellations without storing personal data.
  3. 3Freeze the test battery and catch the regression when the spec or the code changes.
  4. 4Approve, version, and turn off tools through the catalog, without a code deploy.
