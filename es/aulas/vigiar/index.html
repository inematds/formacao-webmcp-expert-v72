Clase 6 · 15 min

Vivir con una API que cambia: vigilar la spec, Chrome Status y el changelog de MCP

La API de WebMCP ya cambió de lugar una vez: de navigator a document. Va a cambiar de nuevo antes de cualquier versión estable. En vez de enterarte por el visitante, guarda lo que decían las fuentes el día en que pasó la batería y deja que un script compare. ¿Cambió? Corre la batería y lee antes de tocar nada.

Comenzar la clase

En esta clase vas a

  1. 1La línea de tiempo del cambio navigator → document
  2. 2Qué vigilar: spec, Chrome Status, MCP y el SDK
  3. 3La base guardada y la comparación
  4. 4Qué hacer cuando la vigía dice MUDOU

Objetivo: guardar la base del día en que pasó la batería y vigilar la spec, Chrome Status y MCP, con el caso navigator → document como ejemplo.

02 · Qué vigilar y dónde

Páginas públicas, sin clave y sin costo.

1. Spec

La fecha en la parte superior del borrador y los nombres de la IDL (registerTool, getTools, executeTool, toolchange).

Si vuelve el nombre antiguo o aparece un método nuevo: hora de releer.

Fuentewebmachinelearning.github.io/webmcp

2. Chrome Status

El estado ("Proposed" el 19/10/2026) y las versiones del origin trial (149 a 156).

El trial termina en el 156: anótalo en la agenda, junto con el token.

FuenteJSON público de Chrome Status, entrada 5117755740913664

3. MCP

La página de versionado dice la revisión actual (2026-07-28) y el changelog dice qué cambió.

El Registry está en preview, con aviso de cambio y reset: no dependas de él.

4. Tu SDK

El servidor del kit responde server/discover con las revisiones que habla (2026-07-28).

La versión del paquete siempre fija; subirla es una decisión, con batería antes.

03 · La base grabada

Generada con --gravar el día en que la batería pasó. Es la que la vigía compara.
